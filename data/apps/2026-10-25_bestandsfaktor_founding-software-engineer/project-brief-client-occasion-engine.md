# Project brief: Client Occasion Engine (repo slug: client-occasion-engine)

Status: planned (on the Bestandsfaktor CV, 2026-10-25). Must be built before submitting. No link on the CV.

## Goal
A small, API-first backend that does what Bestandsfaktor's engine does in miniature: scan an insurance broker's client portfolio, detect service occasions, prioritise them, route each client to the next action and channel, draft a personalised message with an LLM, and record outcomes so each rule's performance can be monitored over time.

## Scope (1–2 days with Claude Code)
- Synthetic portfolio: ~500 clients, contracts (GKV, Hausrat, Haftpflicht, Altersvorsorge), sums insured, premium history, life data (age, household). Generated by a seed script, no real data.
- Mock broker management system: a tiny FastAPI app exposing `/clients` and `/contracts` (paginated), standing in for a broker system API.
- Integration adapter: pulls from the mock API, upserts into Postgres, idempotent sync with a `last_synced_at` cursor.
- Trigger rules (YAML config): premium increase > X%, Hausrat sum insured below an inflation-adjusted value, coverage gap (no Haftpflicht), age milestones. Each rule = condition + priority + action + channel.
- Prioritisation + routing: score = rule priority × client value; one next action per client per window (dedupe, cool-down).
- LLM message drafting via an LLM API (LiteLLM so the provider is swappable); template + client facts; output validated (Pydantic, length, no invented numbers: every number in the draft must exist in the input facts).
- Event log: `trigger_fired`, `message_drafted`, `sent` (simulated), `outcome` (simulated: reply, appointment, data updated).
- Monitoring endpoint: `/metrics/rules` → per-rule fired / sent / outcome rate over time (learning curve), plus a small Streamlit or plain HTML chart.
- Tests: pytest for rules, routing, dedupe, adapter idempotency; labelled set of ~50 clients with expected triggers; GitHub Actions CI. Dockerfile + docker-compose (api, mock-bms, postgres).

Out of scope: real sending, real broker data, UI beyond the metrics view, auth beyond an API key.

## Tech stack
Python, FastAPI, Postgres (SQLAlchemy), Pydantic, LiteLLM, pytest, Docker / docker-compose, GitHub Actions.

## Architecture sketch
```
mock-bms (FastAPI) --REST--> sync adapter --> Postgres (clients, contracts, events)
                                                  |
                         rules.yaml --> trigger engine --> prioritise/route --> LLM drafter --> events
                                                  |
                                     /metrics/rules  (monitoring, learning curves)
```
